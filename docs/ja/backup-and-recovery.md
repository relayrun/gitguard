基礎草案 0.1 — 2026-10-28。

権限制御と復元できるコピーは、異なる障害に対処します。基本は独立した機器への自動同期、完全性検査、保護された過去の復元ポイントです。**コンパイルとアプリ起動は任意です。**プロジェクトに応じて手動検査、別トリガー、追加の自動化を選びます。

<a id="personal-and-company-schedules"></a>

## 個人と企業のスケジュール

個人は予備のノート PC を定期的に起動し、設定済みトリガーで同期できます。システム起動とユーザーログインのどちらがトリガーかを明記します。ログイン時のタスクは、そのユーザーがログインする前には動きません。企業では利用可能な独立機器で、毎日の実行、実行漏れへの対応、回数を制限したネットワーク再試行、同時実行制御、確認できる失敗結果を設計できます。

これらは実装の選択肢であり、この手順書が提供する稼働機能ではありません。読むだけでバックアップスクリプトや定期タスクがインストールされるわけではありません。AI の開発アカウントに、全復元版を削除する権限やバックアップ機器の管理権限を与えないでください。

<a id="define-what-the-copy-covers"></a>

## コピーする範囲を定める

main のチェックアウトはサーバー全体のバックアップではありません。ブランチ・履歴、ローカルのみ・未コミットの作業、ソース・文書、必要な依存関係、実行時リソース、外部設定、非公開プロジェクトをどこまで含めるか定めます。秘密情報は適切に保護された復元手順で扱い、公開例や共有用の通常アーカイブには入れません。

Git リポジトリのデータと、ホスティングサービスのメタデータは別です。自前サービス全体の復旧には、整合したデータベース、アカウント・権限、課題・PR、添付、設定、ストレージも必要になり得ます。サービスの復旧はソースコードのビルドとは別に検証します。

更新され続けるミラーは削除も反映することがあります。独立した復元ポイントを保持し、最後の正常版を保護します。実際の復旧要件に応じて保持期間を決め、新しい転送が成功と報告しただけで古いコピーを自動消去しないでください。

<a id="baseline-checks"></a>

## 基本の検査

1. ソース、意図する版・範囲、保存先、アカウント、空き容量を確認し、無関係なデータを保護します。
2. 変更済み・分岐したチェックアウトを上書きしたり、変更を送り返したりせず同期します。意図して fetch した版との厳密な一致を確認します。ローカルブランチがリモートより進んでいても「最新」と表示される場合があります。
3. 定めた範囲を整合した状態で取得し、復元ポイントに一意の識別子を付けます。含める・除くルールと必須ファイルを記録します。
4. マニフェストと関連するソース・ファイル・アーカイブのハッシュを確認します。ZIP を開く、ファイルを数える、ZIP だけをハッシュ化することは、必要なソースを含む証明にはなりません。必須項目の失敗は全体の結果に反映します。
5. 結果を長期保存し、定期的に別の空の保存先へ復元します。完全性検査と復元検査を分け、実際に復元するまでは復元を未検証とします。

<a id="optional-compilation-and-startup"></a>

## 任意のコンパイルと起動

選択した場合、実際に対応するツールチェーンとクリーンビルド手順で復元したコピーをコンパイルします。構成、範囲、読み込まれない・除外されたプロジェクト、依存関係を記録します。アーカイブ自体にキャッシュ出力があれば、復元先が空だったことだけではクリーンビルドを証明できません。元の開発機の未申告ファイルで欠落が隠れないようにします。

過去の教訓として、プロジェクトファイルを保存していても、必要な外部ベンダーのソースが欠ける場合があります。復元後のコンパイルはその発見に役立ちます。ただし、コンパイルだけでは全ての文書、実行時リソース、ホスティング DB、アプリの経路を検証できません。

必要に応じて適切なテスト環境で復元したアプリを起動し、基本機能を確認します。本番への副作用を避けます。文書・静的コンテンツのプロジェクトには、無関係なコンパイラーを必須とせず、リンク、内容、サイトに適した検査を選びます。

ビルド・起動の状態は **未選択・未検証・合格・不合格**で記録します。任意の検査を選ばなかったことは基本バックアップの不合格理由ではなく、転送完了をビルド検証済みと呼ぶこともできません。

<a id="if-validation-fails"></a>

## 検証に失敗した場合

バックアップの欠落、環境要件、アプリの不具合のどれが原因か調べます。対象ルールや申告環境を修正し、新しい復元ポイントを作って復元し、影響する検査を繰り返します。以前の正常版と失敗記録を残します。失敗の証拠を黙って上書きしたり、再検証せず古いバックアップが直ったと主張したりしないでください。
