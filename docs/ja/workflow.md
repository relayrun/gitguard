<a id="read-and-scope-the-work"></a>

## 作業範囲を確認する

対象プロジェクト、ローカルディレクトリ、ブランチ、リモート、公開範囲、現在の許可を特定します。エージェント向けの入口、現在の計画、関連する運用手順を読みます。無関係なステージ済み・未ステージの変更はそのまま残します。編集、コミット、push、PR 作成、リリース公開、サイトのデプロイは別々の操作です。既に与えられた許可は引き継ぎますが、一般的な計画を全操作の許可と解釈してはいけません。

<a id="step-1--record-the-local-change"></a>

## ステップ1 — ローカル変更を記録する

変更ファイル一覧と差分を確認し、変更に適した検査を実行します。公開する資料は、当面ローカルだけに保存する場合でも、**コミット前に**[公開内容の点検](public-content-review.md)を済ませます。対象ファイルだけをステージし、許可されたローカルコミットを作成します。そのコミットの識別情報、内容、作業ツリーに残る変更を確認します。

ローカルコミットではアップロードは行われません。通常の編集に付随して、無断で別のリポジトリを初期化したり、リモートを追加したり、保護設定を変更したり、バックアップタスクを作成したりしないでください。状態をクリーンにするために無関係な変更を破棄してはいけません。

<a id="step-2--share-the-branch-and-prepare-the-pr"></a>

## ステップ2 — ブランチを共有し、PR を準備する

現在の許可範囲で、リモートの送信先と実際の対象ブランチに対する差分全体を確認します。最新コミットだけでなく、そのブランチの未マージの過去のコミットも確認対象です。アップロード前に、公開してよい内容の範囲を再確認します。

許可された作業ブランチを force なしで push します。標準のホームページ・動画の例では、正しいソースとターゲット、タイトルと説明の案、実際の検査結果を用意し、人が Web 画面でリクエストを作成します。入力案を準備しただけの状態を、PR 作成済みと報告してはいけません。

導入先は、対応する PR の作成・更新を AI に別途許可できます。その場合に限り操作し、実際の存在と状態を確認します。この例外でも最終マージ権限は与えられません。公開リポジトリに push したブランチやドラフト PR は既に公開されており、マージされるまで非公開という意味ではありません。

ポリシーや権限により拒否されたら、実際の拒否を報告します。管理者セッション、別のトークン、サーバーの直接ポート、コンテナへのアクセス、別の画面で回避してはいけません。内容の競合を解決する際も、許可された操作範囲を勝手に広げないでください。

<a id="human-final-review-and-merge"></a>

## 人による最終レビューとマージ

標準例では、人が OneDev/GitHub の Web 画面でリポジトリのリクエスト一覧を開き、新規作成を選び、候補のソースとターゲットを確認し、タイトル・説明を入力して送信します。別途許可された手順でリクエストが既に作成されていれば、重複作成せず確認します。ブランチの既定候補は承認を意味しません。

人が差分全体、テストの証拠、対象、意図した結果を確認し、最終マージを実行します。この手順では、AI が本人に代わってマージボタン、マージ API/CLI、自動マージを使うことはありません。

レビュー必須化と、人だけがマージできることは別の制御です。レビュー検査が通った後でも AI のアカウントがマージできる可能性があります。技術的に強制されていると説明する前に、両方を検証してください。ボットのアカウントだけでなく、管理者資格情報や既存のブラウザーセッションも保護します。

<a id="after-the-human-confirms-merge"></a>

## 人がマージ完了を伝えた後

1. サーバーで実際にマージされたことと対象を確認します。PR の準備依頼は、マージ完了の報告ではありません。
2. fetch し、レビューした変更とマージ結果を比較します。squash/rebase でコミット識別子が変わることがあります。対象が先に進んでいる場合、リポジトリ全体の一致を要求せず、適切な基点と結果の差分を比較します。同じ基点の squash なら、最終ツリーの一致は有用な証拠です。
3. 整理前に、未コミットの作業、未公開コミット、別の worktree、適用される復元・保持方針を確認します。依頼されていないバックアップを作ったり、整合させるためにローカルだけの作業を上書きしたりしないでください。
4. リモートとの関係が許す場合、ローカルの保護ブランチを fast-forward します。分岐していれば、reset で消さず停止して説明します。
5. 整理の許可範囲で、完了を検証できた作業ブランチだけを削除します。サーバーで既に削除済みなら、古い追跡参照を prune し、ブランチを作り直しません。squash は単純な祖先関係による削除判定を満たさない場合があるため、別の許可された方法を使う前に内容と保持すべき作業を確認します。
6. 実際のブランチ・作業ツリーの状態、保持した作業、未解決事項を報告します。ローカル整理はデプロイやリリース公開と同じではありません。

<a id="keep-the-rules-portable"></a>

## 他の環境でも使えるルールにする

命名とレビューの規約はリポジトリ所有者が定めます。OneDev と GitHub では制御やアカウントの仕組みが異なりますが、共通の順序は変わりません。[安全性検証](security-acceptance.md)で予定したポリシーと検証済みの権限境界を分け、GitHub 固有の違いは[対応ガイド](github.md)を参照してください。
