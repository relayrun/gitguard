Базовый черновик 0.1 — сверено с документацией GitHub по приведённым ссылкам 2026-10-28.

OneDev остаётся основным подробным примером Git Guard. GitHub — второй пример: применяйте тот же [ежедневный процесс](workflow.md), [проверку безопасности](security-acceptance.md) и [рекомендации по резервному копированию](backup-and-recovery.md). Глава сопоставляет возможности, а не описывает текущие настройки конкретного репозитория.

| Общее требование | Реализация в GitHub |
| --- | --- |
| Локальная подготовка и коммит | Обычная локальная работа Git без отправки на сервер на этом этапе |
| Разрешённая удалённая совместная работа | Отправка рабочей ветки и подготовка текста; в стандартном примере человек создаёт PR через веб |
| Обязательный review и защита main | Подходящие branch protection/rulesets и требования к review |
| Ограничение force-push и удаления защищённых ссылок | Соответствующие разрешения остаются выключенными; исключения проверяются |
| Финальное слияние человеком | Отделение личности/учётных данных ИИ от полномочий человека; обязательный review сам по себе не даёт исключительного права на merge |
| После слияния человеком | Проверка результата, безопасная синхронизация локальной main и очистка только завершённой ветки |

Документация GitHub предусматривает защищённые ветки и rulesets веток/тегов для публичных репозиториев на тарифах Free; доступность для приватных зависит от тарифа. Не делайте из этого вывод о доступности всех расширенных функций или push rulesets. [Защищённые ветки](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) · [Rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

Обязательные одобряющие reviews сами по себе не определяют, кто может выполнить слияние после одобрения. Значение имеют административные исключения классической защиты, разрешённые субъекты, списки обхода rulesets, права приложений и доступные человеческие учётные данные. Документированные ограничения push для подходящих репозиториев организаций — одна из мер, которую следует рассмотреть вместе с обязательными PR; проверьте фактическую личность, прежде чем заявлять исключительное право человека на merge. Владелец должен сохранять отдельный контроль над администрированием, удалением репозитория и изменением правил.

В стандартном примере человек проходит создание pull request: проверяет base (цель) и compare (источник), вводит заголовок/описание, отправляет, просматривает diff и результаты проверок, затем лично выполняет merge. Требуемые независимые одобрения остаются обязательными; создание PR не означает его одобрение. В [общем процессе](workflow.md) описан отдельно разрешаемый вариант создания PR силами ИИ.

GitHub также поддерживает автоматическое слияние; этот процесс оставляет финальное выполнение человеку. Не включайте автоматизацию как побочное удобство. Не предполагайте, что токен позволяет запись рабочих веток, но запрещает все слияния только потому, что назван ограниченным.

Пример reverse proxy для собственного OneDev не превращается в прокси перед сервисом GitHub. Перенесите цель защиты на собственные механизмы GitHub: учётные записи, правила, права приложений и проверенные пути доступа.

Перед применением проверьте фактический тариф, видимость репозитория, действующие правила и исключения, затем выполните общую матрицу в разрешённой одноразовой среде. Написание этой главы не меняло настройки репозиториев и не выполняло негативные тесты безопасности.
