# Настройка OneDev: права ИИ и проверка человеком

[English](../en/onedev.md) · [简体中文](../zh-CN/onedev.md) · [日本語](../ja/onedev.md) · [Deutsch](../de/onedev.md) · [Français](../fr/onedev.md) · [Español](../es/onedev.md) · [Português (Brasil)](../pt-BR/onedev.md) · [Русский](onedev.md)

[Главная Git Guard](../../README.ru.md) · [Быстрый старт](README.md)

Это руководство **RelayRun Git Guard** объясняет разделение прав человека и ИИ, защиту main, ограничение путей обхода review и независимые восстанавливаемые копии в собственном OneDev. ИИ создаёт коммиты и отправляет рабочие ветки в пределах разрешения; человек создаёт запрос, проверяет его и выполняет финальное слияние через веб.

**Git Guard предназначен для отдельных пользователей и команд с Git-репозиториями, не только для пользователей OneDev.** OneDev и GitHub — примеры настройки. Другие платформы управления Git могут применять [общие принципы сотрудничества и защиты](workflow.md), проверяя настройки и результаты с учётом своих возможностей. Эта глава показывает OneDev, а [руководство GitHub](github.md) — другой пример. OneDev является сторонней платформой, а не продуктом RelayRun.

Черновик для проверки 0.1. Версия интерфейса и диагностики: **OneDev 14.1.0**. Это привязанный к версии пример, а не рекомендация установить старый выпуск без проверки актуальной поддержки. [Процесс](workflow.md) · [Проверка безопасности](security-acceptance.md) · [Вариант GitHub](github.md)

<a id="visible-ai-assisted-setup"></a>

## Видимая настройка с помощью ИИ

Можно настроить платформу вручную или поручить ИИ следовать этому руководству и навыку настройки через видимый интерфейс Computer Use. Сначала определите точный проект, исполнителя, изменяемые настройки и откат. Человек одобряет этот объём и может наблюдать действия; скрытого или постоянного административного доступа это не подразумевает.

Для административных настроек используйте временную контролируемую сессию, предназначенную для этих изменений. Человек вводит чувствительные данные, не помещая их в чат, скриншоты или файлы репозитория. Не используйте административную сессию для обхода запрещённой повседневной операции. По окончании перечитайте настройки, проведите проверку в соответствующих границах, завершите привилегированную сессию и вернитесь к ограниченной повседневной личности. Если доступный интерфейс не позволяет выполнить шаг, сообщите об этом и оставьте его человеку; не заявляйте о нажатии, которого не было.

Наблюдение за экраном помогает понять настройку; защиту обеспечивают реально действующие права и их испытания.

<a id="1-select-a-deployment-boundary"></a>

## 1. Выбрать границу развёртывания

Предпочтителен независимый компьютер, сервер или NAS с архитектурой и поддержкой контейнеров для выбранного выпуска OneDev. Сервер, контейнерная среда, хранилище, резервные копии и административные учётные данные должны быть недоступны личности ИИ-разработчика. На одном хосте нужны явные права ОС/файлов; один Docker такого разделения не создаёт.

Используйте официальную инструкцию и [параметризованный пример](../../examples/onedev/README.md). До запуска выберите поддерживаемые версии/digests образов, независимое место данных, TLS-вход и способ восстановления. Пример открывает только loopback-шлюз, не предоставляет Docker socket и отключает прямые HTTP/SSH-пробросы на хост. Это начальная конфигурация, не испытанная production-установка. Контейнерные сборки могут потребовать отдельно спроектированный executor.

<a id="2-establish-separate-identities"></a>

## 2. Создать отдельные личности

| Где проверить | Что сделать | Что подтвердить |
| --- | --- | --- |
| Administration → Users / Groups | Разделить человека-рецензента/администратора, ИИ-участника и backup-личность только для чтения | Реальное членство и учётные данные, включая наследуемый доступ |
| Administration → Roles | Проверить права кода, управления проектом и другие права выбранной роли | Названия роли недостаточно; ИИ не должен владеть/управлять проектами и менять защиту |
| Project → Settings → Authorizations → Users / Groups | Выдать только нужный проектный доступ; проверить родителей | Backup-личность читает лишь нужный репозиторий; права ИИ соответствуют заявленной модели |
| Project → Settings → General | Проверить родительский проект и фактическую роль по умолчанию | Нет случайного анонимного/стандартного доступа или наследуемого владения |

Отключённый переключатель «Manage Pull Requests» у эталонной роли Code Writer относится к управлению/массовым операциям; он не доказывает невозможность финального merge для автора кода. Отдельно проверьте право слияния после действительного человеческого одобрения. Не предоставляйте повседневной личности ИИ человеческую браузерную сессию или административный токен. Описанная контролируемая сессия настройки временная; сохранять её для обычного Git нельзя.

<a id="3-initialize-and-protect-the-target-branch"></a>

## 3. Инициализировать и защитить целевую ветку

Создайте нужную защищённую ветку в контролируемом человеком процессе настройки до включения правила, запрещающего её создание. Не отключайте защиту регулярно ради инициализации или ремонта ветки силами ИИ.

Откройте **Project → Settings → Code → Branch Protection**. В эталонном интерфейсе выберите защищённую ветку, часто `main`, и нужных субъектов; пример использует `anyone`. Проверьте порядок: в этой версии локальные правила предшествуют родительским, действует первое совпавшее. Дочернее правило может скрыть более строгое родительское; проверьте фактическое поведение.

| Параметр | Что учесть |
| --- | --- |
| Prevent forced push | Включить для защищённой ветки; в одноразовом репозитории проверить реальный отказ неразрешённого переписывания |
| Prevent deletion | Защитить ветку; удаление репозитория — другое право |
| Prevent creation | Решить после инициализации; не заменяет защиту обновлений/review |
| Required reviewers | Выбрать независимого человека через селектор; проверить полученное выражение и аккаунт |
| Required builds / signatures | Выбрать по проекту с реально запускаемыми проверками и доверенными ключами подписи |
| File/tag protection | Задать только нужный объём; правила ветки не доказывают защиту тегов или выпусков |

Ранний пример изначально не имел обязательного рецензента; требования добавили позднее. Запрет force-push **не запрещает** обычный прямой fast-forward push. Проверьте его явно. Именованный рецензент, который одновременно подаёт PR, может обрабатываться эталонной реализацией иначе; раздельные человеческая и ИИ-личности необходимы. Не заявляйте исключительное право человека на merge, пока оно не прошло отдельный тест.

Сохраняйте осознанное изменение настроек только в пределах разрешения. Перечитайте значения и соответствующие личности; скриншоты показывают настройку, но не её применение.

<a id="4-set-pr-defaults-without-confusing-responsibilities"></a>

## 4. Настроить значения PR, не смешивая обязанности

Откройте **Project → Settings → Pull Requests**. Проверьте, локально ли каждое поле или наследуется.

- **Default merge strategy:** пример использует Squash. Значение по умолчанию не запрещает другие стратегии.
- **Default assignee:** ответственный за работу, не обязательный рецензент.
- **Delete source branch after merge:** необязательная очистка, зависящая также от прав исполнителя. Не делайте вывод, что нужно удалить все старые ветки.
- Перед передачей всегда проверяйте источник, цель, diff, заголовок и проверки. Человек проводит review и финальный merge; ИИ не нажимает merge и не включает auto-merge.

После squash проверьте интегрированное изменение относительно реальной истории цели. Разные ID коммитов сами по себе не означают потерю содержимого. Следуйте общему процессу безопасной синхронизации и ограниченной очистки.

<a id="daily-human-request-creation"></a>

### Повседневное создание запроса человеком

После того как ИИ отправит разрешённую ветку и предложит заголовок/описание, человек открывает страницу pull requests, создаёт запрос, проверяет источник/цель, вводит текст и отправляет. Прочитайте diff и реальные результаты проверок/review перед личным подтверждением merge. См. [полную передачу работы](workflow.md). Если создатель также обязательный рецензент, проверьте правила одобрения своей версии; при необходимости привлеките другого уполномоченного человека вместо ослабления защиты.

<a id="5-optional-rest-ingress-restriction"></a>

## 5. Необязательное ограничение REST на входе

При собственном размещении шлюз может запретить пространство REST, разрешив нужные веб/Git-пути. Это описано в [примере шлюза](../../examples/onedev/README.md). Некоторые интеграции могут перестать работать; выбирайте схему только при соответствии потребностям сервиса.

Проверьте все маршруты: прямой backend-порт, SSH, альтернативное имя хоста, IPv6, туннели, авторизованные браузерные сессии, серверные задачи и управление контейнером/хостом. Блокировка endpoint на прокси не доказывает блокировку остальных путей. Включите нормализованные пути, варианты регистра/кодирования, реальные операции Git и необходимые WebSockets в проверку. Сетевой сбой не подтверждает отказ в правах.

<a id="6-two-common-pitfalls"></a>

## 6. Две типичные проблемы

<a id="pr-source-branch-is-not-suggested"></a>

### Исходная ветка не предлагается для PR

В версии 14.1.0 предложения исходной ветки учитывают email автора последнего коммита и подтверждённые адреса вошедшего пользователя. Проверьте автора и нужного пользователя. Через его Email Addresses добавляйте только подконтрольный ему адрес и завершайте обычное подтверждение. Поведение администратора не означает, что обычный пользователь может обойти подтверждение.

Снова откройте создание PR и проверьте источник и цель. Допустим и ручной выбор ветки. Это исправляет предложение, но не выполняет автоматический merge и не даёт одобрения. Не меняйте глобальную Git-личность и не переписывайте историю лишь ради появления подсказки. Явно выбранный источник имеет приоритет.

<a id="a-ready-pr-remains-marked-work-in-progress"></a>

### Готовый PR остаётся помеченным как незавершённый

Эталонная реализация считает заголовок, начинающийся с `wip` или `[wip]` без учёта регистра, незавершённой работой и блокирует merge. Это **не** запрет всех заголовков, начинающихся с английской буквы. Правило касается заголовка PR, который мог быть получен из сообщения коммита или ветки.

Убирайте маркер только после реальной готовности. Обязательные review, проверки и финальное слияние человеком остаются необходимыми; блокировка WIP не доказывает границу права merge. Проверьте правило в установленной версии.

<a id="7-acceptance-and-recovery"></a>

## 7. Проверка и восстановление

Используйте [общую матрицу](security-acceptance.md) и [шаблон доказательств](../../templates/security-acceptance.csv). Начните с инвентаризации только для чтения; перед тестами отказа в одноразовом репозитории получите соответствующее разрешение. Записывайте исполнителя, версию, пути, меру контроля, состояние до/после и фактическую причину отказа. Необъяснённая ошибка или отсутствующий тест — «не проверено».

Поддерживайте независимые восстанавливаемые версии репозиториев **и** данных/конфигурации сервиса по [руководству backup](backup-and-recovery.md). Обновляемый клон не является полным резервным копированием OneDev. Сборка и запуск приложения необязательны и не проверяют каждую серверную базу или вложение.
