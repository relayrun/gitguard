基础指南审阅稿 0.1 — 2026-10-28。

权限限制和可恢复副本解决不同的问题。基础是自动同步到独立设备、完整性检查以及受保护的历史恢复点。**编译与启动程序均为可选项**，用户根据项目选择手工执行、单独触发，或追加自动脚本。

<a id="personal-and-company-schedules"></a>

## 个人与公司触发方式

个人可以定期开启另一台笔记本，让已配置的任务自动同步；要写清触发点是系统启动还是用户登录，登录触发不等于未登录就能运行。公司可以使用可用的独立设备每日定时执行，并考虑错过任务、网络重试、并发控制与失败提示。

这些是实施选项，不是本文已经交付的脚本能力。阅读指南不会安装备份脚本或定时任务。不要让 AI 的开发身份能够管理备份设备或删除全部历史版本。

<a id="define-what-the-copy-covers"></a>

## 明确备份范围

一个主分支检出目录并不是完整服务器备份。需要写清是否包括其他分支及历史、本地独有或未提交工作、源码与文档、必要依赖、运行资源、外部配置及私有项目。凭据通过适当保护的恢复流程保存，不能放进公开示例或用于分享的普通压缩包。

Git 仓库数据和托管平台元数据不同。完整自建服务恢复还可能需要一致的数据库、账号和权限、工单与 PR、附件、配置和存储。服务恢复要独立于源码编译验证。

持续更新的镜像会同步删除。保留独立恢复点并保护上一份已知良好版本；按实际恢复需求选择保留策略，不能因新传输报告成功就自动抹掉历史副本。

<a id="baseline-checks"></a>

## 基础检查

1. 核对来源、目标版本与范围、目的位置、身份及空间，保留无关数据。
2. 同步时不覆盖脏目录或分叉历史，不向源端推回改动。核对最终版本确实等于预期拉取版本，避免本地分支领先却被当成已同步一致。
3. 按声明范围获得一致副本，使用唯一恢复点编号，记录包含、排除与必需文件。
4. 对照清单及相关文件、源版本和归档校验值。能打开 ZIP、文件计数或 ZIP 自身哈希，不能单独证明必需源码都已包含；必需检查失败应导致结果失败。
5. 保留持久结果，按适当周期恢复到独立空目录检查。完整性检查与恢复检查分别记录，没做恢复就标明恢复未验证。

<a id="optional-compilation-and-startup"></a>

## 可选编译与启动验收

选择编译时，使用真实支持的工具链及干净构建步骤，记录配置、覆盖项目、未加载或排除项目和依赖。恢复目录为空，不代表归档里不存在缓存产物；不能依赖原开发机上未声明的文件来掩盖遗漏。

一个有价值的经验是：备份可能包含项目文件，却漏掉编译所需的第三方源码，在恢复端编译时才发现。但编译成功仍不能证明所有文档、运行资源、托管数据库或应用功能都能恢复。

也可以选择在适当测试环境启动恢复后的程序，检查基础功能，避免实际生产副作用。对于纯文档或静态内容项目，选择相关的链接、内容或网站检查，不硬套无关软件的编译器。

编译和启动各自记为“未选择”“未验证”“通过”或“失败”。未选择可选检查不代表基础备份失败；只完成传输也不能称为编译验证通过。

<a id="if-validation-fails"></a>

## 发现问题之后

区分备份遗漏、环境要求或应用本身缺陷，修正包含规则或声明的环境，生成新恢复点，再恢复并重验受影响部分。保留上一份良好版本及失败记录；不能改写失败回执，也不能未经重验就声称旧备份已修好。
